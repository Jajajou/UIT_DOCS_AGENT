# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each constraint below was discovered through failure.
> Acknowledge each one explicitly before proceeding.

- [ ] CONSTRAINT: MinerU VLM garbage-output bug — the deployed MinerU 2.5-Pro instance can return HTTP 200 OK on `/file_parse` while the actual layout/content extraction is degenerate (thousands of repeated `!` chars, truncated for length, `content_list len=0`). A 200 status does NOT mean valid output — always inspect `content_list` length in the response before declaring success.

**Do not proceed until all boxes are checked.**

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Trusting HTTP 200 as success signal for MinerU | `/file_parse` returned 200 OK on the first (killed) attempt despite the VLM emitting garbage `!!!!` output and empty `content_list` | blocking | After any `/file_parse` call, parse the JSON response and check `len(content_list) > 0` and that text is not degenerate/repetitive before treating the test as passed |
| Blocking SSH curl calls without background+poll pattern | First test attempt ran `curl` synchronously over SSH inside the Bash tool, hit the 120s tool timeout, looked "hung" | advisory | Always run remote long OCR calls via `nohup ... & echo pid $!` then poll with `ps -p <pid>` / tail logs, as done for the retry (PID 1897) |
